# 开发规范

## 权限

1. 远程连接服务器

你有一台服务器可以连接，命令是

```bash
ssh Guqq
```

已经通过公钥进行免密处理。服务器使用 Slurm 作业调度系统。所有会产生明显计算负载的任务，包括训练、推理、评测、批量数据处理、编译和长时间运行的脚本，都必须通过 Slurm 提交，禁止直接在登录节点运行。

以下轻量管理操作可以直接在登录节点执行：`git pull`，查看代码和文件，使用 `sinfo`、`squeue`、`sacct` 等命令查看集群或作业状态，创建和检查虚拟环境，安装依赖，下载资源，以及执行不会产生明显计算负载的配置检查、文件校验和短时诊断命令。如果无法确定某个命令是否属于轻量操作，应通过 Slurm 提交。

在网络连接出现问题时，考虑

```bash
bash net.sh
```

1. 许可操作

下面的操作都得到我显式的授权。

- 本地：负责代码编辑、提交到github、从服务器上 scp 结果数据。

增、删、改、查， git push, git add, git commit, git clone, scp。单个文件达到或超过 10 MiB 时视为大文件，不得通过普通 Git 提交；数据集、模型权重、checkpoint、运行日志和批量结果等生成物无论大小都应默认加入 `.gitignore`。如果确实需要把大文件传到服务器（如服务器网络不可用），请使用 scp 从本地传输。

- 服务器：查看集群情况、负责拉取代码同步、任务提交。

查看集群情况、查看代码、执行 `git pull` 或使用 Slurm 系统提交任务。不得在服务器上使用编辑器、脚本或补丁直接修改受 Git 管理的源码；源码修改必须在本地完成并提交，再通过 `git pull` 同步到服务器。允许 `git pull` 更新服务器工作树，也允许在任务约定的虚拟环境、依赖缓存、数据集、模型、日志、checkpoint、临时文件和结果目录中创建、修改或删除文件。不得覆盖不属于当前任务的环境、数据或实验结果。每次连接服务器前，必须在 docs/agents/gpu.md 中记录连接用途，并检查是否在权限内；连接后，必须先执行 `git pull` 拉取最新代码，然后再执行任务。

- 网络：搜索资料、查找或下载文献、代码仓库、数据集、模型权重、libraries、packages 和 wheels 等任务所需资源。

上述资源均允许直接在服务器上通过互联网下载，包括文献、代码仓库、数据集、模型权重、libraries、packages 和 wheels。下载和解压等轻量操作可以在登录节点执行；若下载后的校验、转换、预处理或编译会产生明显计算负载，必须通过 Slurm 提交。下载内容应放入任务约定的数据、模型、缓存或环境目录，不得借下载操作直接修改受 Git 管理的源码。

## 开发规范

1. 进度更新

在推进过程中，在 docs/agents/update.md 中记录每次进度更新，粒度按照 git commit 级别。

任务开始时，在 docs/agents/state.md 的“当前状态”和“当前计划”中记录计划。执行过程中可以更新这两个区域，使其始终反映当前有效状态，但不得删除或覆盖已有的“变更记录”。进入、完成或阻塞一个阶段，以及对计划作出实质调整时，必须在“变更记录”末尾追加带时间的记录，说明状态变化、调整原因和下一步。即：当前状态快照允许更新，过程历史必须追加保留。

1. 单元测试

开始一个实现单元前，必须计划与目标对应的测试，并在 docs/agents/test.md 中记录测试范围和预期结果。实现单元是可以独立验收的一项功能、修复或重构，不要求在每次编辑单个文件前重复记录测试计划。代码、配置或脚本修改应根据风险安排单元测试、集成测试或静态检查；仅修改文档时不强制编写单元测试，但必须检查链接、路径、命令和格式等与修改相关的内容。每个实现单元在形成验收提交或合并到正式分支前，必须完成对应测试，并将实际结果记录在 docs/agents/test.md 中。若测试依赖服务器 GPU，可先创建并推送仅用于远程测试的临时验证提交；该提交必须位于临时分支并明确标记为未验收。服务器通过 `git pull` 获取该提交并使用 Slurm 执行测试。测试通过后，方可整理为验收提交或合并。

测试失败的代码不得作为验收提交或合并到正式分支；允许保留用于复现和修复的临时验证提交。不得因测试失败而降低测试标准，除非有充分的证据说明测试与原来计划的要求不符。

1. 虚拟环境

在服务器上配置环境前，需要先使用 python 创建虚拟环境，并在 docs/agents/env.md 中全面记录虚拟环境的创建、安装包、版本等信息，确保代码在不同环境下的可复现性。

1. 代码结构

在计划中，应当明确代码结构，划分模块，明确每个模块的功能和接口。每个模块应当有单独的文件夹，并在文件夹中包含 README.md 文件，说明模块的功能、输入输出、使用方法等。

1. 经验积累

在同一个任务连续失败3次后，必须在 docs/agents/lessons.md 中查找失败原因和经验教训；若没有，则需要在 docs/agents/lessons.md 中记录新的经验教训。包括但不限于：

- 网络连接经验
- 任务提交经验
- 代码调试经验
- 数据处理经验
- 模型训练经验
等。

另外，当涉及代码结构、功能或环境配置等方面的经验时，应当在 docs/agents/lessons.md 中记录。只有当经验体现为影响代码正确性、兼容性或安全性的非显然约束时，才在相关代码附近添加注释；环境配置、集群操作和一般调试经验不写入业务代码。架构和模块边界方面的长期决策应记录在对应模块的 README.md 或专门的架构决策文档中。
